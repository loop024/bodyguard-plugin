# 追加改善の計画・進捗

作成日: 2026-09-21。対象: Spigot 1.21.8 / Java 21。既存データ形式とコマンドを維持する。

## 計画

1. チャンク管理: 毎周期の候補選択で既存チケットを優先し、上限超過時の不要な読み込み・解放を抑える。上限と所有者別上限は維持する。
2. 停止時保存: 護衛保存の成否を呼び出し元へ返し、失敗時には明確なログを残す。
3. 処理時間: 護衛保存と10 tickごとの管理周期の直近所要時間を計測し、管理者の `/bg status server` に表示する。
4. 文書: 保存形式番号と存在しない文書リンクを更新し、手動確認方法をここに記録する。

## 進捗

- 調査完了: チャンク候補は周期ごとの巡回開始位置で変化し、上限超過時はチケットの解放・再取得が起こり得る。
- 実装完了: 有効な既存チケットを優先し、候補が上限を超えても周期ごとのチケット入れ替えを抑える。全体上限と所有者別上限は維持する。満杯の間に新しく増えた候補は、枠が空くまで待つ。
- 実装完了: `forceSave()` が成否を返し、停止時の失敗を重大ログへ記録する。`SafeYamlFile` 自体の失敗理由ログも残る。
- 実装完了: 管理周期と護衛保存の直近所要時間を記録し、管理者の `/bg status server` にミリ秒で表示する。保存がまだ発生していないときは「記録なし」とする。
- 実装完了: READMEの `players.yml` 形式を4に更新し、存在しない確認文書へのリンクを現存文書へ変更した。
- 静的確認: 呼び出し元、表示用プレースホルダー、リンク先、変更差分を確認。ビルド、テスト、サーバー起動は利用者が実施する。

## 利用者による手動確認

1. 検証用サーバーを止め、`plugins/BodyGuard` フォルダを別の場所へコピーしてバックアップする。
2. コマンドプロンプトで `build.bat` を実行し、できた `target/BodyGuard.jar` を検証用サーバーへ入れる。
3. `config.yml` の `guard-management.max-loaded-chunks` を `1` にして `/bg reload` を実行する。異なるチャンクに護衛を2体置く。`/bg status server` のチケット数が1以下で、動かしていない護衛の読み込み状態が短時間で繰り返し切り替わらないことを確認する。2体とも常時読み込まれるわけではない。確認後は元の設定へ戻して `/bg reload` を実行する。
4. `/bg status server` に巡回時間と護衛保存時間が表示されることを確認する。護衛の召喚または移動後、保存時間が「記録なし」から数値へ変わることを確認する。
5. 護衛を召喚してサーバーを正常停止し、再起動後も同じ護衛が残ることを確認する。停止時の保存失敗は通常の確認では再現不要。
6. READMEのリンクが開け、保存形式番号が実際の `players.yml` と一致することを確認する。
