# BodyGuard 全面改良・確定実装仕様案

作成: 2026-09-20 / 状態: 提案・実装未着手。
本書の「する」は今後の実装仕様を表す。現行動作を保証する記述ではない。

## 1. 制約と成功条件

- Java 21、Spigot API `1.21.8-R0.1-SNAPSHOT`、既存Mavenと `build.bat` を維持する。
- Windows 10で導入可能にする。この製品はJavaプラグインであり、XAMPP・Python・データベース・追加の必須プラグインは使わない。
- `plugin.test.com.bodyGuard` のパッケージと `plugin.yml` のmainを維持する。Paper専用API、NMS、リフレクションによる内部AI操作は導入しない。
- 開発担当はテスト・ビルド・サーバー起動を実行しない。コードの読み取り確認と文書更新は行う。実機確認は利用者が担当し、未確認を完了扱いしない。
- 既存UUID、所有者、契約世代、操作台帳、友人、相棒、お気に入り、名前、役職、警備地点を維持する。
- 旧コマンド・権限・画面への入口を残す。互換性に影響する挙動変更は本書で明記する。
- 護衛が読み込めない場合は状態として扱い、別のMobを生成して穴埋めしない。

リリース条件: 全チケットがコード上完了、利用者の必須手動確認が合格、P0不具合が未解決でないこと。「コード上完了」と「実機合格」は別列で管理する。

## 3. 既存仕様を守る範囲

召喚・勧誘、対応12種類、OP召喚のみ上限免除、勧誘の上限、通常戦闘AI、攻撃力・移動速度の既定値、保護アイテム、初回ガイド、金床名前変更、クリック操作、履歴、解除と完全削除の違いを維持する。

名前はコマンド1～64文字・GUI1～50文字と既存の色指定を維持する。移動先は既存の `LocationUtil.findSafeLocation` を使う。未読み込みチャンクをGUI操作だけで強制ロードしない。既存の管理チャンク上限64、所有者あたり16、1周期の追加2、探索32は変更しない。

本計画で明示的に変える点は、役職選択を循環式から一覧選択式へ変更、一括処理を分割実行、設定反映の一体化、結果表示の細分化、追加設定を有効にした場合の詰まり復帰である。

## 4. 状態モデルと処理順

### 4.1 混ぜてはいけない状態

| 軸 | 用途 | 永続化 |
|---|---|---|
| 契約 | ACTIVE / RELEASE_PENDING / RELEASED / DELETE_PENDING / DELETED / DEAD | 既存のまま必須 |
| 所在 | 読込済み・未読込・所在不明・ワールド不在・隔離 | 既存の観測記録を維持。表示時に契約と分ける |
| 保護指定 | OWNER / ROLE、roleId、最後に選んだUUID、selectionRevision | 既存形式を維持 |
| 動作状態 | 稼働・対象なし・設定不足・所有者不在・移動待ち・保存確認待ち | 新規の実行時DTO。単なる表示変化で保存しない |
| 動作理由 | 下表のenum | 原則実行時のみ。既存の保存項目は互換読込し、起動後再計算 |

理由コード: `NONE`, `OWNER_OFFLINE`, `TARGET_OFFLINE`, `NO_ROLE_CANDIDATE`, `ROLE_DISABLED`, `ROLE_UNDEFINED`, `ENTITY_UNLOADED`, `WORLD_UNAVAILABLE`, `CROSS_WORLD_DISABLED`, `STAY_OTHER_WORLD`, `NO_SAFE_LOCATION`, `TELEPORT_REJECTED`, `RETRY_COOLDOWN`, `STORAGE_UNCONFIRMED`, `WORK_BUDGET_EXCEEDED`。

表示例: 「移動待ち：安全な足場がありません」「待機中：保護対象は別ワールドです」。利用者への文章で例外名や内部enumを出さない。status詳細の理由コードは管理・問い合わせ用とする。

### 4.2 1体を処理する順番

1. 契約と隔離状態を確認。終了契約へ通常AIを適用しない。
2. Entity確認。取得できなければ未読込理由を更新して終了。
3. 所有者オフライン凍結を適用。`owner-offline.freeze-guards: true` は役職保護にも優先する既存挙動を維持。選択対象がオンラインでも凍結する旨を画面表示する。
4. OWNER/ROLE対象を再評価。選択変更時は戦闘対象・追従サンプルを消す。
5. 最新の対象に対して戦闘相手を検証。対象なし・設定不足のROLE護衛は無警戒状態とし、攻撃と移動を止める。
6. STAY / FOLLOW / GUARDを実行。STAYは別ワールドへ同行しない。OWNER警備は固定地点、ROLE警備は対象の周囲。
7. 実際に変わった位置等の永続化項目だけdirtyとする。結果は実行時ビューへ反映。

無警戒から復帰するときはモード処理がawarenessを明示設定する。OWNER/STAYの既存動作を役職保留処理で誤変更しない。

### 4.3 役職の選択

選択済みUUIDが適格なら保持する。不適格なら同一ワールド優先、距離の二乗、最終UUID、UUID文字列で決定する。異なるワールド間で距離計算しない。オンライン・生存・非観戦・権限保持を必須とする。role.priorityは表示順専用。

1周期内の役職別候補一覧を共有し、周期を越えて権限をキャッシュしない。現在の対象の適格性は攻撃決定時にも直接再確認する。役職変更、ログアウト、死亡等のイベントで再評価を要求する。GUI描画から対象を選んだり保存したりしない。

候補なしでは過去UUIDを履歴として保持してよいが、それを現在有効な保護対象として使わない。表示は「最終対象」と「現在対象」を区別する。

## 5. 操作サービスと失敗の扱い

### 5.1 共通入口

コマンドとGUIは `GuardActionService` を経由する。サービスが最新の所有者、権限、契約、読込状態、保存可否を確認する。クリック時の表示だけを信用しない。内部呼出しの `GuardManager` メソッドは段階的に委譲し、呼出し元の移行が終わるまで削除しない。

新しい結果型:

```java
enum EffectStatus { APPLIED, UNCHANGED, QUEUED, REJECTED, FAILED }
enum PersistenceStatus { NOT_REQUIRED, CONFIRMED, FAILED, UNKNOWN }
record GuardActionResult(UUID guardId, EffectStatus effect,
        PersistenceStatus persistence, ActionReason reason) {}
record BulkActionResult(UUID requestId, int total,
        List<GuardActionResult> results) {}
```

`ActionReason`: NONE / NOT_OWNER / PERMISSION_DENIED / NOT_FOUND / RETIRED / NOT_LOADED / ALREADY_FULL / SAME_VALUE / INVALID_INPUT / LIMIT_REACHED / ROLE_UNDEFINED / NO_SAFE_LOCATION / TELEPORT_REJECTED / SAVE_FAILED / SAVE_UNKNOWN / SESSION_EXPIRED / BUSY / CANCELLED。移動系の詳細理由は動作理由へ対応付ける。

入力はactor UUIDと対象UUID。プレイヤー操作は実行時にオンラインを再確認する。コンソールの既存server診断・全削除だけは別管理入口に保持する。オンラインプレイヤーを偽造して処理しない。

集計の規則: 全件がAPPLIED/UNCHANGED/QUEUED/REJECTED/FAILEDのいずれか1区分に入る。保存状態の件数は別軸の内訳。例「移動3、対象外2、失敗1。そのうち移動済み1体の保存は未確認」。総数と内訳が一致するようUUIDを重複排除する。

### 5.2 操作別の確定点

| 操作 | 成功とする時点 | 保存失敗時 |
|---|---|---|
| モード・名前・役職・お気に入り・分隊・設定 | 必要な保存が成功 | 確実に未反映なら旧値へ戻す。結果不明は下記保留処理 |
| 回復 | HPが増加 | HPを無理に減らして戻さない。追加の永続設定保存がなければNOT_REQUIRED |
| 呼び戻し | teleport成功 | 移動済みとして表示。位置をdirtyにし再保存。勝手に逆テレポートしない |
| 召喚・勧誘 | 既存の契約登録が確定 | 現行復旧手順を維持。二重召喚しない |
| 解除・削除 | 操作台帳の受付確定、Entityへの反映完了 | 受付済みでEntity不在ならQUEUED。再実行で契約を復活させない |

`SafeYamlFile.UNKNOWN_RESULT` は「絶対に失敗」と同義でない。対象ストレージの後続書込みを保留し、ディスクの再読込・検証でどの版が存在するか確認する。ガード変更はrevisionと変更内容、players変更は候補の正規化DTOと旧DTOを比較する。候補一致は確定、旧値一致はロールバック可能、それ以外・再読込不能は読み取り専用で診断へ出す。保留中の既存save/retryも同じゲートを通す。メモリを旧値へ戻しただけで次のautosaveを許可しない。

### 5.3 戦闘ポリシー

`ProtectionPolicy` に「攻撃対象にしてよいか」「ダメージを通してよいか」を分けて実装する。所有者・友人・有効な役職対象は攻撃対象にしない。同一所有者護衛も標的にしない。設定で許可する既存の所有者へのダメージ・護衛同士ダメージはダメージ側で判定する。友人と選択中役職対象へのダメージは常に防ぐ。

近接・飛び道具・間接ダメージで同じ判断を使う。飛び道具の命中キャンセルは実際に防ぐ関係だけにし、設定trueでも常に弾をすり抜けさせる不一致をなくす。標的選定とダメージ許可を1つのbooleanにまとめない。

被害防止のイベント処理と援護指令の処理を分ける。前者はHIGHEST、後者はMONITOR・ignoreCancelled=trueで最終ダメージが正のイベントから要求を作り、次tickに相手・対象・契約・権限を再確認して指令する。他プラグインが取り消したダメージから援護を開始しない。MONITOR処理でイベント自体は変更しない。

## 6. 個人設定

司令メニューslot24から27スロットの設定画面を開く。slot10=通常通知、12=GUI音、14=照準表示、16=一覧の初期並び順、22=ガイド再表示、18=戻る、26=閉じる。

- 通知: `INHERIT / TITLE / CHAT`。INHERITは現在のサーバー設定。全体タイトル無効なら個人TITLEでもチャットにする。失敗・保存異常の通知を消す設定は作らない。
- GUI音と照準表示: `INHERIT / ON / OFF`。サーバー側falseを個人ONで上書きしない。
- 初期並び順: 既存STANDARD / DISTANCE / HEALTH_RATIO。新しく一覧を開くときに適用。戻る操作はその画面の並び順を保持。
- 保存が成功するまで有効表示を切り替えない。設定は `players.yml` 形式4に保存する。未知のenumはそのフィールドだけ既定値へ戻して警告。友人・相棒・ガイド履歴を消さない。
- 通常通知は上書き連打を避け、一括操作は受付時と終了時にまとめる。操作本人の通知のみ変更し、既存のワールド効果音まで個人設定で変更しない。

## 7. 分隊

### 7.1 データと基本ルール

所有者ごとに最大8分隊。分隊IDはUUID、表示名は前後空白を除去した1～16文字、色コード・制御文字は禁止。同一所有者内では大文字小文字を区別せず重複禁止。護衛は0または1分隊に所属できる。未所属は画面上だけの分類。

所属は `players.yml` 形式4の各所有者配下に集約する。`GuardData` やPDCへ重複保存しない。召喚直後は未所属。他人の護衛は登録不可。未読込でもACTIVE契約なら所属変更可能。分隊削除は所属を外すだけで護衛を解除・削除しない。削除確認にはこの結果を明記する。

終了契約への参照は表示から除外する。明確にRELEASED/DELETED/DEADとなった場合だけ掃除し、未読込・所在不明・隔離を理由に消さない。起動時に所属が重複していたら分隊UUID文字列順で最初を残し、修復内容を診断する。別所有者・存在しないUUIDは実行対象から除外するが、生データを消す前に保全する。

### 7.2 コマンド（追加）

```text
/bg settings
/bg squad
/bg squad create <名前>
/bg squad rename <分隊ID> <名前>
/bg squad delete <分隊ID> confirm
/bg squad add <分隊ID>       # 見ている自分の護衛を所属変更
/bg squad remove            # 見ている自分の護衛を未所属へ
/bg squad order <分隊ID> <follow|stay|guard|tp|heal>
```

分隊IDの入力は補完とチャット表示を用意する。名前はcreate/rename末尾を連結し空白を含められる。識別は必ずUUIDと所有者。`delete confirm` は分隊定義のみ削除するので、旧 `/bg deleteall` と混同しない説明にする。

新権限: `bodyguard.settings` と `bodyguard.squad` はdefault true、bodyguard.useを前提とし既存admin経路も尊重する。分隊命令はさらに既存bodyguard.mode / teleport / healが必要。bodyguard.adminでも他人の分隊操作は許さない。

### 7.3 分隊画面

一覧画面slot1と司令画面slot23に分隊入口を追加する。既存機能が使っていない装飾位置であることを実装時に確認し、競合があれば変更記録へ代替位置を書いてから作業する。

分隊一覧: 54スロット、4=概要、9～16=最大8分隊、18=未所属、45=戻る、49=作成、53=閉じる。カード左クリックで詳細。作成・名前変更は既存金床入力の仕組みを入力目的別に拡張し、護衛改名と混ぜない。

分隊詳細: 54スロット、4=分隊名と人数、9～35=メンバー27体のページ、36=追従、37=待機、38=警備、39=集合、40=回復、41=追加、42=名前変更、43=分隊削除確認、45=戻る、46=前ページ、49=結果、52=次ページ、53=閉じる。

メンバー左クリックは護衛詳細、右クリックは分隊から外す。追加画面は54スロットで9～44に自分のACTIVE護衛、45=戻る、46=前、49=案内、52=次、53=閉じる。所属済みの別分隊名を表示し、クリックで移籍する旨を記載。既存の一体お気に入り・相棒操作は維持する。

### 7.4 一括指令

受付時にUUID集合とコマンド引数をコピーする。1所有者につき実行中は1件。全所有者を合わせて同時64件までで超過はBUSY。実行直前に対象・所有者・権限・契約を再確認する。分隊命令は所属も再確認し、途中離脱者は対象外、新規加入者は追加しない。

FOLLOW/STAYは各護衛に適用。GUARDは受付時のプレイヤーの足元をOWNER護衛の共通地点とし、ROLE護衛は現在の役職対象周辺警備になる。混在する場合は受付表示に両方の体数を出す。未読込は対象外。ROLE指定は一括命令でOWNERへ変えない。

既存の全員操作も同じキューを使用する。ただし解除・完全削除は既存の永続操作台帳を保持し、揮発性キューだけで受付済みにしない。確認画面のUUIDスナップショット・有効期限・一回限り消費も維持する。

全体で1tick最大8体、1所有者1巡で最大2体をラウンドロビン処理。各UUIDの結果を1回だけ集計する。ログアウト・停止で未着手の通常指令はCANCELLED。反映済みは巻き戻さない。再起動後に通常指令を自動再開しない。GUIを閉じても実行は続き、終了通知を出す。権限喪失なら残件はPERMISSION_DENIED。

## 8. GUIと診断の統一

`GuardView` はUUID、名前、種類、契約・所在・動作理由、モード、HP（不明可）、ワールド、距離（不明可）、役職、分隊を含む変更不能な表示DTOにする。描画はこの値のみ読み、メモリ更新・PDC書込・保存・チャンク要求を行わない。

一覧54、詳細45、司令27、金床の既存寸法を維持する。自動更新でスロットUUIDを入れ替えない。結果や状態が変わったスロットだけ `setItem`。手動更新時だけ並びを再計算。クリック・ドラッグ・数字キー・Shift・オフハンド・金床結果の既存防御を維持する。

詳細の保護対象カードはROLE_PICKERへ移動する方式に変更。ROLE_PICKERは54スロット、9=OWNER、10～44=役職35件/ページ、45=戻る、46=前、49=現在対象、52=次、53=閉じる。役職はpriority降順・ID昇順。再読込後に消えた役職の古いカードは失敗理由を表示し適用しない。

statusは既存引数を維持し、保存の正常/停止/結果不明、読み書き対応形式、最新失敗、通常指令の待ち件数、当周期処理数、予算により繰越した数を追加する。一般プレイヤーには自分の護衛と利用可否のみ、server診断には全体値を表示する。診断は復旧操作やデータ消去を行わない。

## 9. 追従と負荷

新設定は欠落時も下記既定値で動かす。実装前に既存設定検証方式へ対応付ける。

| キー | 既定値 | 有効範囲・意味 |
|---|---:|---|
| `follow.stuck-recovery.enabled` | false | 互換優先で初期無効 |
| `follow.stuck-recovery.seconds` | 4 | 2～30秒 |
| `follow.stuck-recovery.min-progress` | 0.5 | 0.1～2.0ブロック |
| `follow.stuck-recovery.cooldown-seconds` | 10 | 5～120秒 |
| `performance.max-guards-per-cycle` | 100 | 10～1000体 / 10tick周期 |
| `performance.max-bulk-actions-per-tick` | 8 | 1～32体 |
| `performance.max-transfer-attempts-per-cycle` | 4 | 1～16回 / 全護衛合計 |
| `performance.max-hostile-scans-per-cycle` | 16 | 1～128回 / 全護衛合計 |

周期を跨ぐカーソルで公平に巡回する。総数N、処理上限Bの場合、通常巡回はおよそceil(N/B)×10tickに一度となる。リアルタイムの誤射防止はイベント内で常に判定し、予算不足を理由に無効化しない。遅延は診断へ出し、一定のTPSや何千体対応などを保証しない。

詰まり検出はFOLLOWの歩行要求中、同一ワールド、戦闘中でない場合だけ。サーバーtick基準で4秒の開始位置と現在位置の水平移動量が0.5未満なら候補。対象移動距離だけで判定しない。対象UUID変更・モード変更・テレポート・戦闘開始・ログアウト時にサンプルをリセットする。

復帰は既存の安全地点探索で近くへテレポート。別ワールド、STAY、固定警備の新規ワープ、戦闘中の逃走には適用しない。失敗でも10秒の待ち時間を置く。通常の役職ワールド移動失敗もoperation別再試行ゲートを実際に参照し、同じ探索を毎周期繰り返さない。テレポートを拒否する他プラグインを迂回しない。

AI・Entity・World・Inventory・PDCは同期処理のみ。今回は保存の非同期化をしない。先に保存回数の削減と計測を行い、非同期保存が必要なら別設計にする。[Spigotのスケジューラ文書](https://hub.spigotmc.org/javadocs/spigot/org/bukkit/scheduler/BukkitScheduler.html)も非同期タスクからのBukkit APIアクセスを禁止している。

## 10. 保存形式と移行

共通 `StorageSchema` 定義を唯一の版数情報とする。guards=6、playersはT00時点3、個人設定・分隊実装時4、operations=1。SafeYamlFileに根拠不明な版上限を重複記載しない。quarantine等の補助ファイルは既存rootと検証を調べ、root名を勝手にguardsへ変えない。

新規追加例（UUIDの山括弧表記は説明用。実装では実UUID）:

```yaml
version: 4
record-count: 1
players:
  <owner-uuid>:
    # 既存のガイド・友人・相棒キーをそのまま維持して追記する
    preferences:
      notification-mode: INHERIT
      gui-sounds: INHERIT
      action-bar: INHERIT
      default-sort: STANDARD
    squads:
      <squad-uuid>:
        name: 前衛
        members:
          - <guard-uuid>
```

1. 元YAMLの版を先に判定。将来形式なら自動復旧も保存もせず、そのファイル名と対応版をログに出し起動停止する。
2. 旧形式を既存の型・UUID・record-count検証で読む。形式なし等、現行が認める旧入力は保持する。
3. メモリ上で欠けた新項目に既定値を設定。既存キーを落とさない。
4. 書換え前に元ファイルを同ディレクトリへ `players.yml.pre-v4-<timestamp>-<uuid>.bak` のように一度保全する。コピー失敗なら移行保存を止める。
5. 全項目が検証できた候補を一時ファイルへ書き、再読込してから置換。成功時のみ新しい値を採用する。途中失敗は既存SafeYamlFile結果区分を保持する。
6. 再起動しても同じ入力から重複分隊を作らない。移行用backupは通常の `.bak` ローテーションと分け、自動削除しない。

異常な将来形式の識別は専用例外で通常の破損と分離する。バックアップ自体が将来形式なら復旧不可として停止する。新形式を消して旧版へ戻す処理を実装しない。利用者が旧Jarへ戻す場合はサーバー停止後、移行前のプラグインデータと必要に応じてワールドも揃えて復元する。

guards/players/operationsは別ファイルであり、単一の原子的トランザクションとは説明しない。解除時は既存台帳を先に確定し、players内の分隊等の参照掃除は後から再試行できる処理にする。掃除失敗を理由に解除を取り消さない。

## 11. 今回の対象外

装備GUI、経験値・レベル、自動蘇生、護衛取引、所有者共有、SQL移行、Web管理、巡回ルート作成、隊形を保つ高度な経路探索、Paper/Folia対応、対応Minecraft版の更新は追加しない。今回の「分隊」は操作対象のグループで、戦闘力や隊列を変える機能ではない。

公式Mob APIの参考: [Spigot Mob](https://hub.spigotmc.org/javadocs/spigot/org/bukkit/entity/Mob.html)。公開Javadocは閲覧時点で26.x系を表示するため、1.21.8への新メソッド採用根拠にしない。実装は既存ソースで使用中のAPIと、必要ならローカルの1.21.8依存資料に照合する。API参照だけでコンパイル確認済みと記録しない。
