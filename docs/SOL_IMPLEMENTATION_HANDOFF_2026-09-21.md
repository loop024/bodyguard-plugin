## 最初に読むこと

このファイル単独で仕様を推測しない。[実装仕様書](COMBAT_PERFORMANCE_SPEC_2026-09-21.md)が動作の契約、[計画・進捗](COMBAT_PERFORMANCE_PLAN_2026-09-21.md)が最新の作業台帳、[手動確認](COMBAT_PERFORMANCE_MANUAL_2026-09-21.md)が利用者向けの確認手順である。

今回の利用者の最終指示は**計画書を書くこと**。本引き継ぎ文書を作成した時点では実装は停止している。下の開始プロンプト等で実装を指示されたときだけ再開する。

## 1. 最初の15分で確認するもの（時間は目安、作業上限ではない）

- 作業ルートと利用者のAGENTS指示を確認する。テスト禁止は以降も継続する。
- git statusと直近ログを読む。途中コードはauto-backupコミットに含まれる。cleanを「変更なし」と取り違えない。
- BodyGuard.javaの新getterの実際の呼出し元を検索する。
- GuardTask.run、GuardManager.trackLoadedEntity/setMode/setProtection/teleportGuardを読む。
- CombatListener、TargetListener、GuardStorage.readState、SafeYamlFile.failを読む。
- 仕様書T01～T10をソースで再確認する。既に修正されていれば根拠を書き、再実装しない。
- 現在のguards schemaが7であることを確認する。ソースを6へ戻して途中の利用者データを読めなくしない。
- 現時点のビルド成否を推測しない。コードはコンパイル未確認。

## 2. 実装順序と段階ごとの終了条件

### S0: 途中データ構造の完成

- [ ] GuardDataの不変設定とruntime状態を整理する。
- [ ] trackLoadedEntityの再構成でtacticsを保持する。可能なら契約オブジェクトを安易に置換しない。
- [ ] policy変更だけで巡回番号を初期化しない。
- [ ] 追跡episodeと一時的な命令解除を分離し、tick基準へ統一する。
- [ ] GuardTacticsの正本をYAMLとし、未使用のPDC encode/decodeと誤解を招くコメントを整理する。
- [ ] guards version7、旧キーなし、未知enum、不正point番号、UUID違い、巡回の組合せを静的に追う。

終了条件: 読込→再構成→保存のどこでもtacticsが消えない。まだGUIから巡回を公開しない。

### S1: 戦闘方針の入口から出口まで

- [ ] CombatIntentと中央controllerを用意し、既存の禁止判定を再利用する。
- [ ] 自己防衛、所有者防衛、役職防衛、攻撃支援、自然AI、索敵を方針表どおりに接続する。
- [ ] PASSIVEをターゲットだけでなく発射済み/間接ダメージにも適用する。
- [ ] targetイベント内でmob.setTargetを呼ばず、キャンセルを上書きしない。
- [ ] changePolicyに所有者・権限・存在・保存結果の共通サービスを用意する。
- [ ] policyコマンド、Tab、権限、GUIスロット1、messagesを接続する。

終了条件: enumの全値が実際の戦闘経路で使われ、LEGACYは既存の標的取得規則、その他は方針表に従う。

### S2: 撤退と遠距離補助

- [ ] エピソード継続時間・保護中心からの距離・視認喪失で撤退する。
- [ ] 同じ敵への連続命令、敵A/B切替でタイマーが消えない。
- [ ] 撤退中の新規標的取得を止め、帰還後＋最短待ち時間の条件で解除する。
- [ ] ROLE/OWNER/STAY/GUARDごとの帰還先を接続する。
- [ ] 対応射手のMob種類＋実装備を確認し、安全な後退だけを行う。
- [ ] 自動復帰・射手後退・通常追従が同じ更新で重ね掛けされない制御順序を確認する。

推奨優先順: 存在/契約確認→凍結/対象資格→禁止対象解除→撤退判定→撤退帰還→合法戦闘/射手補助→巡回/追従/待機→非戦闘の復帰。

終了条件: 追跡をやめても直後に同じ敵へ戻らない。移動先なしで強制移動しない。

### S3: 配置分散

- [ ] GuardFormationの半径clampによる重複を修正する。
- [ ] 体格混在での重複、空き不足、安定スロット、予約解放を実装する。
- [ ] 追従到着判定と遠距離閾値を分離する。
- [ ] 一括/単体呼び戻し、OWNER/ROLEの自動追従・復帰へ接続する。
- [ ] enabled=falseの従来経路とキャッシュ解放を確認する。
- [ ] 一括の成功数と保存未確認を維持する。

終了条件: 空き不足が成功扱いにならず、同じ場所への強制重ね置きで無制限を装わない。

### S4: 巡回と他操作の整合

- [ ] add/remove/start/stop/clear/list、任意の自分の護衛UUID、Tabを実装する。
- [ ] UUID省略の視線指定と、遠い地点編集のUUID指定を両方用意する。
- [ ] 同一ワールド2～16地点、到着待ち、戦闘中の停止、安全復帰を実装する。
- [ ] GUARD/OWNER制約、FOLLOW/STAY/ROLE/recall時の巡回停止を同一保存にする。
- [ ] 地点番号runtimeと再起動先頭再開を説明する。
- [ ] GUIスロット37/38、利用権限、保留理由を接続する。

終了条件: 巡回を始めた後の通常操作で、再起動時に隔離される不正な組合せが残らない。

### S5: 登録・位置・状態の索引

- [ ] UUID/契約世代の中央insert/replace/removeフックを作る。
- [ ] ACTIVE数、所有者別護衛、保存位置チャンク別護衛、AI登録を更新する。

### S6: AI更新の公平性と時間枠

- [ ] 明示操作・台帳・死亡・正常停止・保存失敗再試行は即時/既存の順序を維持する。

- [ ] UNKNOWN_RESULTの書込停止を回避しない。

終了条件: 保存回数を減らすために重要操作の受理や成功表示の意味を変えていない。

入口文書に以下の形式で追記する。

```markdown

- 対象要求: M... / P...
- 変更ファイル・メソッド:
- 仕様上の判断と理由:
- 既存挙動への影響:
- 保存・rollback・権限の扱い:

- 残件:
- 次の着手先: ファイル名 / メソッド名 / 具体的な変更
```

## 4. 中断・エラー時の引き継ぎ

- 自動バックアップが作業中にコミットしても続ける。担当者が勝手に履歴を戻したり、clean化目的で利用者変更を捨てたりしない。
- 予期しないソース変更を見つけたら差分と進捗を読み直し、既にできた修正を重ねない。
- APIの有無に確信がなければ既存依存/API資料を読む。テスト禁止を理由にメソッド名を推測して接続しない。
- 仕様と既存実装が食い違う場合は、既存データ・安全性を保つ具体案を記録して修正する。完了に見せるために要求を黙って削らない。
- 実装を止める場合は、未接続のクラス名、保存形式の変更状況、起動可能性が未確認であることを必ず書く。

## 5. 最終報告の形式

```text
大項目1・2の全12項目をコード上で実装しました。
主な変更: ...
旧設定/保存データ: ...
制約: 時間予算は協調的であり、単一保存やチャンクロードには遅延が残ります。
テスト・ビルド・実機確認は未実施です。
確認手順: docs/COMBAT_PERFORMANCE_MANUAL_2026-09-21.md
```

全項目が実装できていないときにこの完了文を使わない。残ったIDと理由を列挙する。
