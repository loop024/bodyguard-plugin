# 役職保護・ワールド間追従 設計書

## 1. 目的と前提

対象は Spigot 1.21.8 / Java 21 の既存 BodyGuard。護衛の所有者、契約、UUID、既存3モード、保存と復旧の仕組みを利用する。ここでいう「役職」は、権限プラグインなどがプレイヤーへ付与する **権限ノード** と定義する。たとえば `bodyguard.role.king` を付与されたプレイヤーを「king」の対象とする。LuckPerms などのグループ名を直接読む仕様にはしない。権限ノードなら追加依存なしで判定できる。

これは実装仕様であり、現時点でコードは変更していない。役職名を別プラグインのグループ名そのもので指定したい場合は、権限ノードへの対応付けをそのプラグイン側で設定する。

## 2. 利用者から見える仕様

### 2.1 対象選択

- 管理者が `config.yml` の `role-protection.roles` に役職ID、権限ノード、優先順位を定義する。役職IDは英小文字・数字・ `_` ・ `-` の1～32文字。権限ノードは空文字禁止。
- 所有者が護衛ごとに `/bg protect <役職ID>` を設定する。`/bg protect owner` は従来の所有者保護へ戻す。`/bg protect status` は視線先の護衛の設定と現在の保護対象を表示する。GUI詳細画面にも同じ選択肢と状態を追加する。
- 役職の候補はオンラインの生存プレイヤーのみ。候補が複数なら、同一ワールド内で最も近い人、次に最終選択UUID、次に UUID の文字列昇順で一意に決める。ただし、いったん選んだ対象が適格である間は他の候補へ切り替えない。再起動や再ログイン後も最終選択UUIDを使って復帰する。
- 所有者もその役職を持つ場合は候補になれる。権限を失う、ログアウトする、死亡する、観戦モードへ変わる場合、対象を解除して再選択する。候補がいなければ護衛は現在地点で待機し、役職設定は保持する。無関係なプレイヤーへ切り替えない。
- `bodyguard.admin` は設定・再読み込みを管理できるが、他人の護衛の対象変更は専用の管理者コマンドを別途設計しない限り許可しない。通常操作は既存の `bodyguard.use` と所有者チェックを必須とする。

### 2.2 モード

| モード | owner 対象 | 役職対象 |
|---|---|---|
| 追従 | 従来どおり所有者を追う | 選択中の役職プレイヤーを追う。別ワールドへ移ったら安全地点へ移動する |
| 待機 | 従来どおり現在位置を守る | 現在位置を守る。対象のワールド移動には同行しない。攻撃が起きた同一ワールド内だけ支援する |
| 警備 | 従来どおり固定の警備地点を守る | 対象を中心とする移動警備。対象が別ワールドへ移ると追従して警備中心を移す |

役職対象の警備は既存の固定地点警備と意味が異なるため、GUIでは「対象の周囲を警備」と明記する。対象が未選択の間は移動・交戦を停止する。役職対象が復帰したら直前のモードで再開する。`teleport.different-world: false` の場合はワールドをまたぐ自動移動を行わず、GUIと `/bg protect status` に「別ワールド移動は設定で無効」と表示する。

### 2.3 保護と戦闘

- 保護対象への被ダメージが確定したとき、同一ワールド・設定射程内の自分の護衛だけが加害者を狙う。対象プレイヤーが攻撃した相手への援護は既存 `combat.assist-owner-attacks` と同じ設定で制御する。
- ターゲット候補は `isForbiddenTarget` に必ず通す。所有者、保護対象、フレンド、同一所有者の護衛への近接攻撃・飛び道具・間接ダメージを防ぐ。攻撃してきた相手が保護対象でも反撃しない。
- 他のプレイヤーが同じ役職を持っていても、現在選択中の1人だけをこの護衛の保護対象とする。所有者の全護衛を一括で動かす既存 `commandGuardsToTarget(ownerId,...)` はそのまま流用しない。`guardId` と選択中対象UUIDで絞る経路を新設する。
- 異なるワールドの敵へターゲットを持ち越さない。移動前に戦闘状態と Mob ターゲットをクリアする。警備半径と帰還距離は既存 `guard-mode` 設定を利用し、追跡が範囲を超えたら中断する。

## 3. ワールド間移動の状態機械

`TARGET_UNAVAILABLE` → `TARGET_SELECTED` → `SAME_WORLD` / `WORLD_TRANSFER_PENDING` → `ACTIVE`。世界が未ロード、候補なし、安全地点なし、チャンク読み込み上限到達なら `WAITING` とし、次回の低頻度タスクで再試行する。各回の失敗は既存 `reportFailure` の抑制付きログへ渡す。

1. サーバーメインスレッドで対象のオンライン・生存・役職権限と護衛契約 `ACTIVE` を再確認する。
2. `PlayerChangedWorldEvent` / `PlayerRespawnEvent` は移動要求フラグを立てるだけにし、対象の位置が確定した次のタスクで実行する。既存 `GuardTask` の10 tick周期を使い、新しい護衛ごとのタスクを作らない。
3. 護衛が読み込み済みなら `LocationUtil.findSafeLocation` で到着先を探し、成功した場合だけ `mob.teleport` する。対象ワールドが利用不能、到着地点が危険、テレポートが失敗なら現在位置と保存座標を変更しない。
4. 護衛が未読み込みなら勝手に別の Mob を生成しない。既存の管理チャンク処理で元の Entity を確認してから移動する。上限に達したら保留として可視化する。重複生成は禁止。
5. 成功後、戦闘状態を消し、`lastLocation` を実位置で更新し、役職対象の警備では移動警備中心も対象位置で更新する。PDC と `guards.yml` の整合を既存の保存手順で確保する。保存失敗時は復旧可能な状態として警告し、成功扱いの通知をしない。
6. ワールド移動中に対象が再移動・ログアウトした場合は古い要求を破棄し、最新の対象UUID・ワールドUUIDを再判定する。ワールド名だけで同一視しない。

## 4. 保存形式と互換性

- `GuardData` に `protectionKind` (`OWNER` / `ROLE`)、`roleId`、`selectedTargetUuid`、`selectionRevision` を追加する。既存記録は `OWNER` として読む。未定義役職IDの記録は消さず「設定不足」として停止する。
- `GuardStorage` の形式バージョンを上げ、読み込み時に型・文字長・役職IDを検証する。壊れたレコードの隔離は既存 `quarantine.yml` の経路を使う。役職が単に設定から消えた場合はデータ破損と扱わない。
- Entity PDC に同じ役職指定と選択UUIDを持たせる。YAMLとPDCのどちらが正しいかは既存の契約世代・保存リビジョンのルールに従い、競合時に別人への保護を推測しない。変更操作は `setMode` と同様に保存成功を確認し、失敗ならメモリとPDCを元へ戻す。
- `SavedPosition` のワールドUUIDを使い、ワールド名再利用による別ワールドへの誤移動を防ぐ。既存の `owner` モード、友人リスト、護衛名、契約の解除・削除データは移行時に維持する。

設定例（実装時にキーの検証と既定値を `BodyGuard` に追加する）:

```yaml
role-protection:
  enabled: true
  roles:
    king:
      permission: bodyguard.role.king
      priority: 100
    medic:
      permission: bodyguard.role.medic
      priority: 50
```

優先順位は役職一覧の表示順だけに使い、複数候補から保護対象を選ぶ規則とは混同しない。権限プラグインで `bodyguard.role.king` を対象プレイヤーに付与してから指定する。

## 6. エラー回避の受け入れ条件

「エラーが絶対にない」は保証できないため、実装完了の条件を明確にする。無効な設定は理由を示して採用しない。対象・ワールド・Entity が不在でも例外を出さず保留する。護衛を重複生成しない。保存失敗時は設定変更を成功表示しない。チャンク読み込み上限を守る。ログには護衛UUIDと失敗箇所を記録し、毎 tick 同じ警告を出さない。リロード・再起動後も役職指定が残る。権限の変更後は次回タスクで対象を再判定する。全ての Bukkit Entity API はメインスレッドから呼ぶ。
